Di dalam satu database, transaksi dijamin ACID: semua
berhasil atau tidak sama sekali
A

Atomicity

Semua operasi berhasil, atau tidak ada yang berhasil

Contoh: Pesanan & stok tersimpan bersama, atau keduanya batal
C

Consistency

Data berpindah dari satu status valid ke status valid lain

Contoh: Stok tidak pernah bernilai negatif
I

Isolation

Transaksi bersamaan memberi hasil sama seperti dijalankan berurutan

Contoh: Dua pembeli tidak mendapat unit terakhir yang sama
D

Durability

Perubahan tetap tersimpan setelah commit, meski terjadi kegagalan

Contoh: Server mati setelah COMMIT, pesanan tetap ada

Setiap transaksi lokal..
  • Menyelesaikan pekerjaannya secara atomik di satu
    layanan
  • Memperbarui database milik layanan itu
  • Memicu langkah berikutnya lewat event atau pesan
Konsekuensinya
Konsistensi tercapai pada akhirnya (eventual), bukan seketika. Di antara langkah, data boleh sementara berbeda antarlayanan

Dua sistem, dua penulisan

Database dan broker tidak bisa dibungkus satu transaksi, jadi salah satunya bisa berhasil sendirian.

Kasus A: DB berhasil, event gagalLayanan crash setelah commit. Layanan Stok tidak pernah tahu; pesanan menggantung di MENUNGGU.
Kasus B: DB rollback, event terkirimLayanan Pembayaran menagih pesanan yang sebenarnya tidak pernah tersimpan.

CREATE TABLE outbox_messages ( id BIGINT AUTO_INCREMENT PRIMARY KEY, aggregate_type VARCHAR(50), -- Order, Payment aggregate_id VARCHAR(50), -- order_code event_type VARCHAR(50), -- OrderCreated payload JSON, -- pesan event status VARCHAR(20) DEFAULT 'PENDING', processed_at TIMESTAMP NULL -- NULL: belum);
BEGIN; INSERT INTO orders (order_code, total_amount, status) VALUES ('ORD-123', 150000, 'PENDING'); INSERT INTO outbox_messages (aggregate_type, aggregate_id, event_type, payload) VALUES ('Order', 'ORD-123', 'OrderCreated', '{"total":150000}');COMMIT; -- tersimpan berdua secara atomik dalam 1 transaksi

id & created_at

Menjaga urutan antrean event (FIFO) sama persis dengan urutan mutasi data.

status & processed_at

Relay mengambil baris status PENDING, lalu menandai PROCESSED saat diteruskan.

payload & aggregate

Menyimpan data lengkap event agar consumer dapat langsung mengeksekusi langkah.

2 cara memindahkan event keluar:

Tabel outbox + polling

Relay membaca tabel outbox secara berkala, misalnya tiap beberapa detik, lalu mengirim ke antrean.

Kelebihan
  • Mudah dipahami dan dipasang di MySQL/PostgreSQL
  • Urutan terjaga lewat id dan stempel waktu
Kekurangan
  • Ada jeda sesuai interval polling
  • Menambah beban baca ke database

Change Data Capture (CDC)

Database sendiri menerbitkan setiap perubahan data ke sebuah stream; relay membaca stream itu.

Kelebihan
  • Tidak perlu tabel tambahan
  • Perubahan tertangkap hampir seketika
Kekurangan
  • Bergantung pada fitur database (mis. DynamoDB Streams)
  • Lebih sulit disiapkan untuk proyek kecil
Outbox menjamin event tidak hilang, tetapi
event bisa terkirim lebih dari sekali

Pesan Duplikat

Relay bisa mengirim ulang. Consumer harus idempoten: catat id pesan yang sudah diproses dan abaikan yang sama.

Urutan Event

Kirim event dalam urutan yang sama dengan urutan perubahan database. Gunakan nomor urut atau antrean FIFO.

Transaksi Rollback

Jangan pernah mengirim event dari transaksi yang dibatalkan. Outbox otomatis mencegahnya.

Lintas layanan

Outbox hanya menjaga satu layanan. Untuk proses lintas layanan, gabungkan dengan saga.

Apa yang gagal

Proses relay berhenti (server restart, error koneksi ke broker). Event menumpuk di tabel outbox.

Dampak

Pesanan tersimpan, tetapi stok tidak direservasi dan pembayaran tidak ditagih. Pembeli melihat “Diproses” terlalu lama.

Cara mendeteksi

Pantau jumlah baris sent_at IS NULL dan umur event tertua. Beri alarm jika ada event belum terkirim lebih dari 5 menit.

Cara menangani

Hidupkan ulang relay; backlog terkirim berurutan. Consumer idempoten mengabaikan duplikat. Saga yang melewati batas waktu dikompensasi.

outbox backlog (status PENDING): 0
Saga dan outbox membeli konsistensi lintas
layanan dengan harga kompleksitas

Manfaat

  • Data konsisten tanpa mengunci banyak database
  • Layanan tetap longgar dan bisa diskalakan sendiri
  • Event tidak hilang walau layanan crash

Biaya & kompleksitas

  • Harus menulis kompensasi untuk setiap langkah
  • Debugging dan pemantauan lebih sulit
  • Tabel outbox, relay, dan broker tambahan

Keterbatasan

  • Konsistensi tercapai belakangan, bukan seketika
  • Kompensasi bisa gagal
  • Anomali data perlu ditangkal sendiri

Alternatif

  • Satu database (modular monolith) bila belum perlu dipisah
  • Transaksi terdistribusi untuk lingkup kecil berisiko tinggi
  • Tidak cocok bila langkah saling terikat erat atau siklik
